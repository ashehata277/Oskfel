Team Zone Headers Review

This review covers the time problems that the team-zone-headers work found in ProjectService and how each one was fixed. They are grouped into recurring patterns, so we can agree on the rule behind each fix and not only the fix. Each pattern also notes where the same problem appeared in the other services and apps in this feature.

The model this PR moves to

One rule applies everywhere: instants are stored and sent as UTC, and the team's zone is applied only at the edges. The edges are the points where a person's idea of a day, a month or a printed date meets the data. Each request carries the team's time settings in headers:

Intowork.TeamTimeZoneIANA zone, for example Europe/London. Required on every request; a missing or invalid zone gets 400. Intowork.TeamDateFormatDisplay format, default dd/MM/yyyy. Used by the apps; the ProjectService time kit no longer reads it. Intowork.TeamTimeFormatDisplay format, default HH:mm. Used by the apps; the ProjectService time kit no longer reads it. Intowork.TeamNameIdentifies the team on the request. Background work reads the team name from the message instead.

In ProjectService, code reads the time only through IDateTimeProvider, and that interface has a single implementation, DateTimeProvider. UtcNow never needs a zone. The team-aware members (TeamNow, ToTeamTime, DayOf, StartOfDayUtc, DayRangeUtc) use the team zone. Inside a request the zone comes from the header. Background work sets it with await clock.UseTeamAsync(teamName, token), which reads the service's copy of the team. The single clock design section explains how it works.

The other services still use the first iteration: RequestDateTimeProvider and TeamDateTimeProvider behind IDateTimeProvider, TimeProvider for "now", and ITeamClocks.ForTeamAsync(teamName) for background work. Rolling the pilot out to them is an open question.

Single clock design (ProjectService pilot)

The first iteration left each class to choose between three clock types: TimeProvider for "now", IDateTimeProvider for team time in a request, and ITeamClocks for team time in background work. Two classes implemented IDateTimeProvider, and dependency injection picked one by context. The pilot keeps one injectable type with one implementation. The clock decides where the zone comes from, and a handler that needs a team says which team, in one line.

Rules for UseTeamAsync

  • Call it only when the handler's code path reads a zone member, directly or through a service or repository it calls. A handler that only needs UtcNow does not call it, so a message for a team this service hasn't seen yet does not fail for no reason.
  • Call it once per message, before any zone member is read. A second call, or a call after the zone was read, throws InvalidOperationException, so a scope can never switch team part way through.
  • A missing team name, an unknown team or a team without a valid zone throws TeamTimeUnavailableException. Let it propagate, so the message is retried and then dead-lettered.
  • The team name comes from the event however that event names it (TeamName, Teamname, Team). Events need no marker interface, and their wire shape is unchanged.
  • Today no ProjectService event handler reads a zone. The four handlers that inject the clock use only UtcNow, and every zone read is on an API request path.

Why each message still gets its own scope

The Common.Messaging event bus (2.1.7) resolves each handler from the root service provider and runs sessions concurrently. If the scoped clock came from the root, two messages for different teams would share one instance, and one team's zone could overwrite the other's. RunEachEventInItsOwnScope() (Intowork.Jobs.BackgroundService/Events/Scoping/) wraps every handler registration in ScopedEventHandler<TEvent, THandler>, which opens a DI scope per message and builds the handler inside it. The wrapper knows nothing about teams. The ordered and Baton customer buses inherit the same bus, so the wrapper covers them too. It is called last in the BackgroundService Program.cs. It could move into Common.Messaging later, which would fix the same problem in every service.

Kit layout: the Intowork.Common.Time package

The kit is now a NuGet package in CommonLibs (CommonLibs/Intowork.Common.Time, branch feature/1.6.0/team-zone-headers), with its own pipeline azure.pipelines.build.yml, built like the other CommonLibs packages: feature/* and develop publish 1.0.0-alpha.{buildId}, stage publishes an RC, main publishes 1.0.0. Every service will reference this package instead of keeping its own Time/ copy; ProjectService is the first. Each folder is its own namespace.

What the pilot removed

  • Second clock types: RequestDateTimeProvider, TeamDateTimeProvider, ScopedDateTimeProvider, ITeamClocks, TeamClockWithFormats and TeamClockScope. TimeProvider is now used only inside the kit, and 92 classes switched to IDateTimeProvider.
  • Team plumbing: ITeamZoneResolver, ITeamScopes, TeamZoneScope, the team-aware event wrapper, and the ITeamEvent marker that had been added to 38 events.
  • Unused helpers: OffsetAt and ForZone. MongoDateParts, TeamHeadersForwardingHandler, TeamToday, ToUtc and the format headers came back in the shared package because other services use them.

Other changes made with the pilot

  • The data seeders are scoped and run inside a startup scope. IntegrationEventPublisherService opens a scope on each loop iteration, so no singleton holds the scoped clock.
  • The API and BackgroundService Dockerfiles need no change: the kit arrives as the Intowork.Common.Time package through the existing NuGet.config.
  • Tests build clocks with TestClocks.WithoutTeam (in each test project's Support/) and TestClocks.InZone(time, zone).

Reviewer checklist

This list is part of the team-date-time skill, which the code-review skill reads as a repository standard.

  • The handler's path reads a zone member → it calls UseTeamAsync first.
  • UseTeamAsync runs before commit or "mark handled", once, with the team from the event, and its exception is not caught.
  • A handler that doesn't read the zone doesn't call it.
  • No marker interface on events, no team-aware wrapper, and no second clock implementation.

Problem patterns

Every pattern below uses the same layout: what went wrong, why it happened, the fix, where the code lives, and the test that now guards it.

1 · The server's clock stood in for the team's clock

DateTime.Now · DateTime.UtcNow · DateTimeOffset.Now
Symptom

Timestamps depended on the host machine. DateTime.Now gives a container's local time, which in AKS is usually UTC and on a developer laptop is something else. Code that read the clock directly also could not be tested at a fixed instant.

Root cause

The static clock was read in handlers, repositories, models and property initializers. Some places mixed Now and UtcNow in the same flow.

Fix
Before · AcquireBulkMoveRegistryHandlerDateAcquired = DateTime.Now,
...
var expiry = DateTimeOffset.Now;
AfterDateAcquired = _clock.UtcNow,
...
var expiry = new DateTimeOffset(_clock.UtcNow);

Commit 3d0027dd made classes inject a clock across 214 files in ProjectService. At first that clock was TimeProvider; with the single clock pilot every class injects IDateTimeProvider.

Guard

Time/ClockUsageTests scans every production .cs file and fails on DateTime(Offset).UtcNow|Now|Today. The same test is in all 15 services. In ProjectService it also fails on any TimeProvider in production code; only the package uses it.

2 · Calendar days were cut at UTC midnight

FilterAndSortExtension
Symptom

A grid filter such as "Transaction date = 30/03/2026" missed rows created between 00:00 and 01:00 London time during BST. Those rows showed up under the previous day instead. The > and <= operators were off by the same hour.

Root cause

The filter parsed the day text as 00:00 with no kind and compared it straight against UTC values in Mongo. The end of the day was built as +1 day − 1 ms. On top of that, the aggregate ApplyFilters overload never passed isDateTimeFilter, so date-time filters on aggregates were treated as day filters.

Fix
Beforevar dt = DateTime.Parse(searchValue, null,
    DateTimeStyles.RoundtripKind);
typedSearchValue = DateTime.SpecifyKind(dt, DateTimeKind.Utc);
...
AdjustToEndOfDay(date) => date.AddDays(1).AddMilliseconds(-1);
AftertypedSearchValue = isDateTimeFilter
    ? ParseInstant(searchValue)
    : DayWindowOf(searchValue, clock);   // clock.DayRangeUtc(day)

Equal        → from <= x && x < to
GreaterThan  → x >= to
LessThanOrEq → x < to

A day filter becomes a half-open UTC window [teamMidnight, nextTeamMidnight). A date-time filter is read as an instant using the invariant culture. Both ApplyFilters overloads now take the clock (commit 4817201f fixed the aggregate one).

Where
The 16 paginated query handlers and their repos (quotations, versions, notes, files, prelims cost and income, external money and valuations, items, materials, catalogues, teams), all through ApplyFilters(filters, clock).
Guard

FilterAndSortExtensionDateTests covers every operator for a London team, both sides of a DST change.

3 · Month windows used the UTC month with an inclusive upper bound

ExternalValuation · one per month
Symptom

The rule "one external valuation per project per month" checked the wrong month for entries close to midnight. Because the end was inclusive, an entry at exactly 00:00 on the 1st counted for two months.

Root cause

The month was taken from the UTC Year and Month of the instant, and the query used <= nextMonth.

Fix

Aftervar month = TeamMonthWindow.Of(clock, transactionDate);

TeamMonthWindow.Of takes the instant's team day, goes back to the 1st of that month, and returns UTC team midnights for that 1st and the next.

4 · UTC instants were printed as if they were local

server-rendered text · PDFs · DTOs with date strings
Symptom

Quotation PDFs were dated with the UTC date. A quote produced at 00:30 BST carried yesterday's date, and so did "uploaded on" for attachments. Over-hire handover erect and strike dates, and the contracted due-strike date worked out from them, could each be one day early.

Root cause

Wherever the backend formats a date into text, the browser never gets the instant to convert. The conversion therefore has to happen on the server, and it was missing.

Fix
Before · QuotationDocumentGeneratorvar now = DateTime.UtcNow;
...
value.ToString("dd-MM-yyyy", Culture)
Aftervar now = _clock.TeamNow;
...
_clock.ToTeamTime(value).ToString("dd-MM-yyyy", Culture)

In GetOverHireHandler, dates are converted to team time first, and the ContractHirePeriod × 7 days are added after that, so the date arithmetic runs on team days.

Guard

QuotationDocumentGeneratorTests and GetQuotationVersionsQueryHandlerTests pin the clock with TeamClockSupport.

5 · UTC values left the API without a Z

UtcDateTimeJsonConverter
Symptom

A DateTime read from Mongo or built in code with Kind = Unspecified was serialised as "2026-03-30T08:00:00". The browser read that text in the device's zone, so the frontend had built regexes to guess what each date string meant.

Fix

One JSON converter, registered by the kit's registration call, writes every DateTime as UTC with Z. On read, an unspecified value is taken as UTC and a local value is converted. Commit f13b9941; the same converter is in all 13 services.

This is what allowed the apps to drop their date-shape regexes. They now call new Date(text) and refuse any date-time without Z or an offset.

Guard

No dedicated test yet. Adding a serialisation test for an Unspecified value would be a cheap follow-up.

6 · A silent London fallback hid missing context

strict team time
Symptom

The first version fell back to Europe/London from configuration, and a meter counted how often that happened. A missing header or a team with no zone therefore produced answers that were plausible but wrong, and never an error. For a London-only customer base, this fallback was hiding exactly the bugs this work set out to find.

Fix
  • Requests: the zone comes only from Intowork.TeamTimeZone. If it is missing or not a known zone, TeamTimeHeaderMissingFilter returns 400 with a ProblemDetails body ("Team time zone required").
  • Background work (messages, jobs): clock.UseTeamAsync(teamName) reads the service's copy of the team (ITeamClocks.ForTeamAsync in the services that have not moved to the single clock yet). A team without a valid zone throws TeamTimeUnavailableException, so the message fails and is retried instead of being processed in the wrong zone.
  • Lazy clock: DateTimeProvider only reads the header when team time is first needed, so UtcNow still works on endpoints that never send the header.
  • Defaults: TeamTimeOptions and the appsettings and helm entries were removed. TeamTimeDefaults keeps only the two display formats. There is no default zone.
Commits

Guard

RequestTeamTimeTests and TeamTimeRegistrationTests

7 · A team's zone could change after its data existed

team settings ownership
Symptom

The first iteration added PUT teamsettings/{team}/timeZone. Changing the zone later would move the meaning of every stored team day, such as absences, month windows and valuation months, without rewriting any data.

Fix
  • The endpoint was removed along with its command, handler, repository method and helm route (commit 8b92ac54, 445 lines deleted).
  • A zone is required when a team is created and checked by TeamTimeSettingsValidator. Editing or updating a team returns TEAM_TIME_ZONE_FIXED if the zone would change.
  • TeamCreated and TeamUpdated now carry TimeZone, DateFormat and TimeFormat, so every other service's copy of the team can resolve the zone for background work.
  • The seeder gives masterteam and the default team Europe/London and publishes the zone in its events.
Guard

CreateTeamTimeSettingsTests, EditTeamTimeSettingsTests, UpdateTeamTimeSettingsTests, TeamEventsTimeFieldsTests, MasterTeamSeedTests

8 · Converting local times to UTC around DST changes

DateTimeProvider · StartOfDayUtc
Symptom

TimeZoneInfo.ConvertTimeToUtc throws for a local time that doesn't exist, such as 01:30 on the morning clocks go forward. For a time that occurs twice, when clocks go back, it silently picks one of the two.

Fix
while (zone.IsInvalidTime(local)) local = local.AddMinutes(30);           // gap → first valid time
if (zone.IsAmbiguousTime(local))
    return local - zone.GetAmbiguousTimeOffsets(local).Max();      // overlap → the earlier instant

Team midnight never falls in a London gap, but these rules matter for other zones and for any time a user enters near 01:00–02:00.

9 · Domain models read the clock themselves

BaseAuditableEntity · constructors · initializers
Symptom

MarkAsCreated, MarkAsUpdated, MarkAsDeleted, about 37 model methods and several = DateTime.UtcNow property initializers stamped time on their own. They could not be tested deterministically, and Mongo deserialisation ran the initializer for nothing.

Fix

Models take a DateTime now from the handler that owns the clock. Examples: MarkAsCreated(performer, now), LinkExpiresOn(now) and QuotationMetadataEventData.From(q, v, now). The initializers were removed once every creator set the value.

New constructor parameters are named after the property they set (raisedDate on ExternalMoney and ExternalValuation, importedAt on Material). The Mongo driver's automatic creator mapping matches parameters to properties by name, so a parameter called now would have broken reads.

Guard

The compiler checks that every call site passes the time, and ClockUsageTests rejects any new static clock read.

10 · Feature work on main and develop kept adding old-style calls

merge drift
Symptom

While this branch was open, main gained application versioning (PR 11140) and develop gained worker item types (PR 11112). Their new code and tests called constructors without the new now parameter, which caused build errors and one conflict in UpdateVersionInfoHandlerTests.cs.

Fix

For each conflicted file, take the incoming version, then add the clock arguments again. Tests pass TestClocks.WithoutTeam.UtcNow and production code passes the injected clock. Main is merged into the PR branch first, and the PR branch then into -develop, so the PR never needs a fix made only on -develop.

Guard

Before each push, git merge-tree of the PR branch against main and of -develop against develop. Both are clean now.

11 · Two clocks for one job

TimeProvider · ITeamClocks · two IDateTimeProvider implementations
Symptom

A handler that needed "now" and a team day injected TimeProvider and ITeamClocks, and then built a third object. Reviewers had to check that each class had picked the right clock for its context. Which IDateTimeProvider a class received depended on DI wiring that its code never showed.

Root cause

The decision about where the zone comes from lived in each caller instead of in the clock.

Fix

One DateTimeProvider, resolved per scope. It works out the zone lazily, and handlers set the team themselves with UseTeamAsync. Each message runs in its own DI scope, so concurrent messages cannot share a clock. See Single clock design.

Guard

TeamScopedClockTests (zone per scope, set once, failures), TeamTimeRegistrationTests, ScopedEventHandlerTests (a separate clock per message, every handler wrapped, Program.cs wraps last), and ClockUsageTests.

For discussion

  1. Strict 400 and older clients. Any caller that doesn't send Intowork.TeamTimeZone, such as an older mobile build, a script or a webhook, now gets 400 on endpoints that use team time. Do we ship the apps first, or keep a short window in which the Gateway always fills in the header?
  2. Day filter or instant filter. In DayWindowOf, plain text such as 2026-03-30 is a team day, while text with Z or an offset is converted to its team day first. Should clients send only plain days for day filters, so there is one shape?
  3. Overlap rule. When a local time occurs twice, we choose the earlier instant. Is that right for every case, including clock-out times entered during the repeated hour?
  4. Unused helpers. Resolved: MongoDateParts and TeamHeadersForwardingHandler were removed with the single-clock pilot. ProjectService calls no other Intowork service over HTTP, and no aggregation groups by team day yet.
  5. Roll out the single clock. Should the other 13 services move to one IDateTimeProvider with UseTeamAsync, and should the scope per message move into Common.Messaging, so each service doesn't need its own wrapper?
  6. Team zone is fixed. If a team ever needs to move, is a data migration the agreed path rather than an endpoint?
  7. Out of scope for now. CommonLibs still has 7 files that read the static clock, and the Frontend near-miss rollback decision is still open.
