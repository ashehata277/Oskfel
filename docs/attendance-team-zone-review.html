AttendanceService · feature/1.6.0/team-zone-headers

Attendance Team Zone Review

The time problems the team-zone-headers work found in AttendanceService and how each was fixed, grouped into recurring patterns. Attendance is where time zones turn into money: clock-in rounding, the 08:00–16:00 pay window, weekend rates and pay weeks all depend on which day and hour a clock reading falls in. Most of the risk in this PR, and most of the testing, is there.

The model this PR moves to

The model is the same as in every service on this feature. Clock readings are stored as UTC instants. A team's zone decides which day, weekday and wall-clock hour each reading belongs to. Requests carry the zone in Intowork.TeamTimeZone. Background work resolves it with ITeamClocks.ForTeamAsync(teamName) from Attendance's copy of the team, which TeamCreated and TeamUpdated keep up to date.

In Attendance this means one thing above all: the clock is no longer a fixed London lookup inside each helper. It is passed down as IDateTimeProvider clock through the wage pipeline: WageRecalculation.Recalculate → travel and break time → wages → bonus → deductions.

Problem patterns

Every pattern below uses the same layout: what went wrong, why, the fix, where the code lives, and the test that now guards it.

1 · London was hard-coded in six places

"GMT Standard Time" · "Europe/London"
Symptom

Every team's wages, clock-in rules and reminders were calculated in London time, whatever the team's zone. A team in any other zone would be paid by London's day and London's summer time.

Root cause

Each helper looked the zone up itself, with an OS switch so that it worked on both Windows and Linux:

Before · repeated six timesprivate static readonly string _timezoneName =
    RuntimeInformation.IsOSPlatform(OSPlatform.Windows)
        ? "GMT Standard Time"   // Windows
        : "Europe/London";      // Linux/macOS
Fix

All six copies were deleted. Each method now takes the team's IDateTimeProvider, and the zone comes from the request header or from the team record. TeamZones.Find accepts IANA ids, and .NET maps them on every OS, so the Windows branch is no longer needed.

Where
WageHelper, WageHelperLegacy, WageWeekDateCalculator, WageCalculatorExtension, ClockInOutTimeCalculator, ReminderService
Guard

WageHelperLegacyTeamZoneTests runs the same cases in more than one zone. ClockUsageTests blocks new static clock reads.

2 · Summer time was handled with ±1 hour patches

WageWeekDateCalculator
Symptom

Week-commencing dates were moved back an hour in summer, and a second method moved them forward again later. The pair only works for a zone whose summer offset is exactly +1 hour. It also breaks if one of the two calls is missed or made twice.

Fix
Beforepublic DateTime AdjustForDaylightSaving(DateTime date) {
    var converted = TimeZoneInfo.ConvertTime(date, tz);
    if (tz.IsDaylightSavingTime(converted))
        return date.AddHours(-1);
    return date;
}
public DateTime RemoveDstSideEffect(DateTime value) {
    // If DST is active, undo the earlier -1 hour shift
    if (tz.IsDaylightSavingTime(local)) value = value.AddHours(1);
    return value;
}
Afterpublic DateTime AdjustForDaylightSaving(DateTime date, IDateTimeProvider clock)
    => clock.ToUtc(date);

public DateTime NormalizeDate(DateTime storedDate, IDateTimeProvider clock)
    => clock.ToTeamTime(storedDate).Date;

public DateTime RemoveDstSideEffect(DateTime value, IDateTimeProvider clock)
    => clock.ToTeamTime(value);

These are real conversions between team wall-clock time and UTC, and they work for any offset. The method names were kept so the change stays small for review.

3 · The pay window was checked against UTC hours

CalcStdWage · CalculateYardWorkerWage
Symptom

The standard wage pays a full day when someone starts by 08:00. The code worked out the summer-adjusted hour and then compared against a literal 8 in UTC anyway. During BST, a clock-in at 08:59 London time is 07:59Z, which passed Hour < 8 and was paid as an on-time start. A yard worker's personal start time (for example 07:30) was read as UTC, which is 08:30 local in summer.

Fix
Beforevar isSummer = tz.IsDaylightSavingTime(cin);
var earliest = isSummer ? 7 : 8;   // computed…
var latest   = isSummer ? 15 : 16;
...
if (((clockIn.Hour == 8 && clockIn.Minute == 0)
     || clockIn.Hour < 8) && duration.Hours >= 8)  // …but not used
Aftervar day = clock.DayOf(clockIn);
var earliest = clock.ToUtc(day.ToDateTime(new TimeOnly(8, 0))).Hour;
var latest   = clock.ToUtc(day.ToDateTime(new TimeOnly(16, 0))).Hour;
...
if (((clockIn.Hour == earliest && clockIn.Minute == 0)
     || clockIn.Hour < earliest) && duration.Hours >= 8)

The yard worker's start becomes clock.ToUtc(teamDay + startTime), falling back to 08:00 team time when the worker has none. Commit 2a6000c notes the result: London pay is unchanged except that a yard worker's start time is now read as local time during BST.

Guard

WageHelperLegacyTeamZoneTests covers a full day from 08:00 to 16:00 in the team zone, a late start paid by the minute, and a yard worker with and without a start time.

4 · Weekdays and day keys came from the UTC date

weekend rates · multi-site days · pay week
Symptom

A clock-in at 00:30 on a summer Saturday is Friday 23:30Z. The Saturday and Sunday rules, expected hours and worker-group start and end times treated it as a Friday shift. Multi-site days were grouped by date.ToString("yyyy-MM-dd") in UTC, so a late shift and an early shift could be merged, or one day could be split in two. That changed how travel and break time were shared out. The bonus period walked back to Friday with from.DayOfWeek, also in UTC.

Fix
Beforeif (IsSaturday(clockIn)) ...
return date?.ToString("yyyy-MM-dd");
while (fromDate.DayOfWeek != DayOfWeek.Friday)
    fromDate = fromDate.AddDays(-1);
Aftervar weekday = clock.DayOf(clockIn).DayOfWeek;
return clock.DayOf(date.Value).ToString("yyyy-MM-dd");
var back = DaysBetween(DayOfWeek.Friday,
                       clock.DayOf(from).DayOfWeek);

WageCalculatorExtension (GetStandardExpectedHours, GetDateKey, IsBreakTimeAllowed, GetStaffRatePerMinute), ClockInOutTimeCalculator, WageHelper.GetRawBonusDataAsync

5 · "Same day" was tested with .Date on UTC values

UserAttendanceRecord · repos · reminders
Symptom

A clock-out searched for "today's open clock-in" with a.ClockInDate?.Date == clockOutDate.Date. During BST, a shift that started after 23:00Z and ended after midnight UTC found no open record. Reminders asked for "today" as DateTime.UtcNow.Date, so between 00:00 and 01:00 London time they read the previous day's allocations.

Fix
  • The attendance aggregate now has a clock. UserAttendanceRecord.FromEvents(events, clock) replays its events with it, and each same-day test is Clock.DayOf(a) == Clock.DayOf(b). A record with no clock throws instead of quietly falling back to UTC.
  • Repositories take a UtcWindow built by the caller (clock.DayRangeUtc(day)) instead of calling .Date and .AddDays(1) themselves.
Guard

UserAttendanceRecordCharacterizationTests, DayWindowCharacterizationTests

6 · Week and period edges were built from UTC dates

WageWeekSnapshotsRepo · WageRecordsRepo
Symptom

Wage periods ended at to.AddDays(1).AddSeconds(-1) in UTC, snapshot searches used an inclusive <= to, and a pay week ended at weekCommencing.AddDays(7). The code itself carried //TODO: Verify time zone correctness. At each edge, a shift could fall into the wrong pay week or period, or be counted twice.

Fix
  • TeamPeriodExtensions.PeriodUtc(clock, from, to) turns a team date range into a UTC window from team midnight to team midnight. CalendarDatesUtc lists the team days in a range.
  • WageRecordsRepo.WeekEnding(weekCommencing, clock) is the team midnight seven team days later. During a DST week, that week is 167 or 169 hours long, not 168.
  • Snapshot reads use WeekCommencing < period.To, and SnapshotSearchStart and CoveredTo are worked out in team days.
  • The three duplicated clock-out filters became WageRecordFilters.
Guard

WagePeriodCharacterizationTests, WageRecordsRepoCharacterizationTests, TeamPeriodExtensionsTests, WagesForPeriodHandlerTests

7 · Reminders ran on one schedule for every team

Hangfire · ReminderJobScheduler
Symptom

The morning and evening clock-in reminders were a single recurring job pair running on London time. Teams in other zones would get them at the wrong local hour, and the job built "today" as a London day for every team.

Fix
  • ReminderJobScheduler.SyncAsync registers one job pair for each distinct, valid team zone, for example Send morning reminders (Europe/London). Each pair runs at 08:00 and 16:00 in its zone using RecurringJobOptions.TimeZone. The old pair without a zone is removed.
  • GenerateMorningReminders(zoneId) builds the zone's day window and keeps only the allocations of teams in that zone (InZoneAsync).
  • A TeamUpdated event re-runs the sync, so a new zone gets its jobs without a deploy. Zones that aren't valid are skipped with a warning.

ReminderJobSchedulerTests, ReminderServiceTests

8 · Background messages could commit work they couldn't finish

integration event handlers
Symptom

Handlers saved data and marked the incoming event as handled before they knew the team's zone. If a recalculation failed afterwards, the message was not retried. ActiveWorkStaffUpdatedHandler also caught and logged the failure, which hid it completely.

Fix
  • The absence, staff-meta and attendance handlers resolve the team clock before any write. A team without a valid zone throws TeamTimeUnavailableException before anything is saved, so the retry starts from a clean state.
  • ActiveWorkStaffUpdatedHandler now rethrows.
  • TeamUpdated always saves the team's new zone and formats. If the wage settings changed and the zone isn't valid, it then throws instead of recalculating wages in the wrong zone.
  • ITeamClockFactory and DefaultTeamClock were replaced by the shared ITeamClocks.
Guard

TeamClockBeforeCommitTests has 9 cases, for example "Absence created for a team with no zone throws before saving or marking the event handled". Also TeamTimeSettingsHandlerTests.

9 · Domain events and models stamped their own time

shared with all services
Fix

The domain events take now from the handler: WageBonusAwarded, WageWeekSnapshotTaken, WageRecordApproved/2, and WageRecordOverridden2/3 (which take date). The User constructor takes DateTime updated, named after the property so the Mongo mapping keeps working, and its mutations take now. ResourceAllocation.UpdateDuration(now) does the same. Handlers that already hold IDateTimeProvider use _clock.UtcNow.

The shared pieces from the other services also apply here: strict header handling, the UTC JSON converter with a Z suffix, and team time defaults kept in code.

10 · Proving the refactor didn't change anyone's pay

characterisation tests · ShadowCompare
Problem

The wage code had little direct test coverage, and this PR changes the signature of almost every method in it. Unit tests written against the new code would only show that the new code agrees with itself.

Fix
  • Characterisation tests (Intowork.Attendance.Core.Tests/Characterization, 13 files) record the current London results first and then require the refactored code to match. Where behaviour changes on purpose, the test records both the old and the new value. Documented_day_boundary_change_of_the_reminder_day_window is one example.
  • Intowork.Attendance.ShadowCompare is a new console tool. It connects read-only to a Mongo database, recalculates the last N pay weeks (26 by default) for every team with the new code, compares the results with the stored wage records, and prints a report. An allow-list file of (staffId, day) pairs records differences that are expected and approved. The exit code lets CI or a release step fail on any unexplained difference.
dotnet run --project Intowork.Attendance.ShadowCompare -- <mongoConnectionString> <database> [weeks=26] [allowList.json]

For discussion

  1. Run ShadowCompare before release. Who runs it against a copy of production data, and who signs off any differences that go on the allow-list? This is the only check here that uses real wages.
  2. Yard worker start times in summer. These are now read as local time, so some summer wages will differ from what was paid before. Does payroll need to know, and do past weeks stay as they were paid?
  3. Legacy edges in WageRecordFilters. The filters keep the old ClockOutDate > From and < To − 1 s. A clock-out at exactly team midnight, or in the last second of the period, is excluded. Should these become half-open [From, To) like everywhere else? That would be a deliberate behaviour change, so it is left for a separate PR.
  4. Day labels look like instants. TeamDayStart returns a team day as a UTC-kind midnight. That value is a label, not the moment the day starts. Should it be a DateOnly, so nobody can compare it with clock times?
  5. Teams without a valid zone. Reminders skip them with only a warning, and their wage messages keep failing and retrying. Do we need an alert or a data check before strict mode reaches production?
  6. Hangfire job ids change. The old Send morning reminders and Send evening reminders jobs are removed when the new per-zone jobs are registered. Check that no other deploy re-creates the old ids.
  7. Found while writing this review. WageWeekSnapshotsRepo.cs on the PR branch starts with two byte-order marks (EF BB BF EF BB BF); main has one. It compiles, but it should be fixed before merge.
