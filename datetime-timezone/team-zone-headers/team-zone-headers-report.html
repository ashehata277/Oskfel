Team Zone via Request Headers

Dates stay UTC in the database and on the wire. Gateway sends each team's time zone with every request. Only the edges use it: one shared date/time control and two pipes in the apps, and the backend code that decides days, "now", day queries and printed times.

The goal on one page

G1 · Storage

Every stored date stays UTC. Nothing is rewritten.

Proof: no migration script; S.5 shows the same wages, apart from the signed-off day-boundary list.
G2 · Edges only

The team zone is used only in the control and pipes, and in backend day, "now", query and print logic.

Proof: ESLint and grep gates (S.7).
G3 · From the request

Zone from Gateway headers. Without a team request (jobs, events, customers, hub) from the team that owns the data, then London.

Proof: contract tests (S.3), fallback counter (S.4).
G4 · No hard-coded zone or UTC day

No Europe/London outside the kit, and no .Date or UtcNow.Date in a day filter.

Proof: grep gates (S.7, 6.9).

Worked example: Toronto device, London team

A user in Toronto (device UTC−4) on a London team (BST, UTC+1) records a clock-in at 08:00 on 15 July 2026.

What the user sees in the control
15/07/2026 08:00 London time
⚠Your device is on Toronto time (UTC−4). Times here are in London time (UTC+1).

The value means 08:00 in London. Converting to UTC removes only London's offset, never the device's. The warning shows only in input controls.

  1. Form value2026-07-15T07:00:00.000Z
  2. Gateway addsIntowork.TeamTimeZone: Europe/London
  3. Stored in MongoDB2026-07-15T07:00:00Z (UTC, as today)
  4. Backend "which day"clock.DayOf(v) → 15 Jul
  5. Day queryclock.DayRangeUtc(15 Jul) → [14 Jul 23:00Z, 15 Jul 23:00Z)
  6. Shown againteamDate → 15/07/2026 08:00 on any device

Customer-portal users

A customer has no team (no claim, no field on BatonCustomer) and can work with several teams. Gateway sends London defaults; the service uses the zone of the team that owns each record and returns teamTimeZone with it (7.6).

SignalR hub

The Gateway route is anonymous because NotificationHub checks the token itself. On connect it reads extension_Team, resolves the zone and keeps it for the connection. Payload dates stay UTC (7.7).

The query rule (Phase 6)

                 every row for D, old and new: the team's midnight (Z3)
                        │        end-of-day row for D
                        │                 │
 ───────────────────────●─────────────────●──────────────────────────●─────►  time (UTC)
                    D-1 23:00Z         D 22:59Z                   D 23:00Z
                        ▲                                            ▲
                   window.From                                  window.To
                        └─────────── clock.DayRangeUtc(D) ───────────┘

 on day D       Date >= window.From  &&  Date < window.To
 before D       Date <  window.From
 D or later     Date >= window.From
 after D        Date >= window.To
 covers D       Start < window.To  &&  End >= window.From

The handler works out the team's day once and passes a DateOnly down. A repository never calls .Date, UtcNow or UtcNow.Date in a filter.
