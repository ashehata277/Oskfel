Frontend: where a date is converted twice, and how to fix it

Frontend-only scope. Every place in Frontend/src/app where a date is converted to (or from) the team zone twice, or converted the wrong way. Each item shows the current code, the fix, and how the value moves. The backend is out of scope here; items that need it are marked.

Two mistakes cause almost all of these. First, a team Date gets turned into text (toString(), JSON, toISOString()), and that text is later read as if it were a real UTC instant. Second, a real instant (new Date(iso), Date.UTC, setUTCHours) is handed to utcDate, teamIso or the formatter, which assume team wall-clock fields.

Three of them crash for everyone: grid date filters (F1), the Gantt chart (F2) and the qualifications form (F17). Most of the others only show when the device zone differs from the team zone, so testing on a UK laptop for a UK team will not find them.

The rules that prevent double conversion

  1. A Date inside the app is always a team Date. Anything else is a string or a CalendarDay.
  2. Wire string → team Date: teamDate in the model, or asTeamDate elsewhere. Never new Date(iso), parseISO or parseJSON.
  3. Team Date → wire: utcDate in bodies, teamIso in queries. Never toISOString(), JSON.stringify or `${date}`.
  4. Team Date → storage, JSON copy, worker, dialog data: teamIso on the way out, asTeamDate on the way back; or structuredClone, which keeps Dates.
  5. Calendar days: teamDayText / calendarDay as yyyy-MM-dd. No Date.UTC, setUTCHours or new Date('yyyy-MM-dd').
  6. Display: pass the value as it is to <app-date-time> or dateFormatter.format. No new Date(value) in front, and no timeZone option.

Types

Team Date → text → shifted again

A team Date becomes text (toString(), JSON.stringify, toISOString()), and the text is later read as a real UTC instant by asTeamDate, teamDate or the formatter.

Real instant treated as a team Date

A Date that is already a real instant (new Date(iso), Date.UTC, setUTCHours, new Date('yyyy-MM-dd')) goes into utcDate, teamIso, the formatter or the date field, which all expect team wall-clock fields.

Two corrections for one offset

An old device or UTC workaround is still applied on top of the team conversion.

Two zones for one value

The value is shown or emitted in one zone and converted with another, or converted before the team zone is known.

Day label read as an instant

The API sends a calendar day as 00:00Z. The frontend reads it with teamDate (an instant shift) instead of calendarDay, so teams west of UTC see the previous day.

export function teamIso(teamDate: Date): string {
  if (!(teamDate instanceof Date) || Number.isNaN(teamDate.getTime())) {

  }

One way to store and revive

Every storage or JSON copy goes through two helpers, so a team Date never becomes a fake instant (F3, F4, F5, F18).

export function toStoredDate(value: Date | null | undefined): string | null {
  return value instanceof Date && !Number.isNaN(value.getTime()) ? teamIso(value) : null;
}

export function fromStoredDate(value: string | null | undefined): Date | null {
  return value ? asTeamDate(value) : null;
}

Mark team Dates in the type system

export type TeamDate = Date & { readonly __teamDate: unique symbol };

export function teamNow(): TeamDate;
export function asTeamDate(value: Date | string | number | null | undefined): TeamDate;
export function teamIso(teamDate: TeamDate): string;
export function utcDate<T>(value: T): T extends TeamDate ? Date : T;

Round-trip tests

Load → save unchanged must not move a value. Run the kit specs and the model specs under each pair below.

const ZONES = [
  ['Europe/London', 'America/New_York'],
  ['Europe/London', 'Asia/Dubai'],
  ['America/New_York', 'Europe/London'],
  ['Asia/Dubai', 'America/Los_Angeles'],
];

it('does not move a value on a save without edits', () => {
  const model = new PrelimsCostTransaction({ date: '2026-06-09T23:00:00Z' });
  expect(teamIso(model.date)).toBe('2026-06-09T23:00:00.000Z');
  expect(teamIso(asTeamDate(teamIso(model.date)))).toBe('2026-06-09T23:00:00.000Z');
});
