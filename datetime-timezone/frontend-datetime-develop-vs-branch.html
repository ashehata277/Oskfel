Date and time handling: develop vs the team-zone branch

For every date-time pattern, this compares what develop does today (before) with what feature/1.6.0/team-zone-headers-develop does (after). Code is copied from both refs. It also lists what the branch still does the develop way, what it breaks, and what to fix before merging.

develop has no concept of a team zone: every date is parsed, compared and shown in the device's zone, with a few UTC hacks that assume the UK.

The branch converts every API date into a team wall-clock Date in the model, uses team-aware helpers everywhere, and converts back on the way out. Device-clock usage dropped from 383 to 5 and | date from 312 to 18.

It is not merge-ready: 6 high-severity regressions break pages for all teams (Gantt, GA, MOR loading, vehicle edit, signed-in time, active-work dialog), and date-only fields, epoch stamps and UTC hacks still need decisions. develop also has one hotfix that needs migrating (M1).

How the branch got here

The approach changed several times. Only the last state is compared below.

  1. 881fff8d2Headers intent. Added the kit and TeamTimeService, swapped pipes and controls. No header was ever sent.
  2. 6881d1195Global HTTP interceptor. Shifted every response date and un-shifted every request body.
  3. 5d32b03d6Per-call plans. Interceptor replaced by toTeamDates(plan), teamDatesAuto and mapToUtc.
  4. 008e610deModel constructors. Response types became classes with teamDate; teamModel helper.
  5. 07b95914fExplicit per-field mapping. new Model(...) plus named xxxToUtc; deep walk removed.
  6. 62967fa14Typed request bodies. Gzip section saves and availability.
  7. 5aa0a1555Settings refresh. Reload team time after a team edit; full reload if the zone changes.
  8. af28d4416Guardrails. check-time-usage, pipeline step, team-day checks, calendarDay, ready guard.
  9. 68017bf6dTeam-aware parsing. asTeamDate, TeamDateFormatter, TeamFormatDateAdapter, committed baseline.

Common points: develop vs branch

C1 · Where the conversion happens

develop: nowhere. Strings and Dates were read in the device zone at each use. Branch: once, in the model constructor (teamDate) on the way in, and once per field (utcDate / xxxToUtc / teamIso) on the way out.

C2 · What a Date means

develop: a real instant shown in the device zone. Branch: a "team Date": its local fields are the team's wall clock and its getTime() is not the real epoch. Every Date that reaches the API must be converted back.

C3 · Epoch vs wall clock

develop: Date.now() for timers, TTLs and ids, which is correct. Branch: ~30 of these became teamNow().getTime(), which shifts with the zone, DST and team switches. Keep Date.now() for anything that is not a calendar value.

C4 · Days vs instants

develop: both were Dates parsed in the device zone. Branch: day questions use yyyy-MM-dd strings (isTeamToday, teamDayText, CalendarDay); moment questions use team Dates. Only bank holidays and absences are true CalendarDays so far.

C5 · Display

develop: 312 | date pipes and ~250 TS formatters with fixed en-GB patterns. Branch: named formats (date, dateTime, dateMedium, …) from team settings via <app-date-time> and TeamDateFormatter. Visible formats change.

C6 · Types

develop: interfaces with string or Date fields, no runtime change. Branch: classes whose fields may change from string to Date at runtime while the type still says string. This is where most new crashes come from.

C7 · Wire format

Both sides assume the backend sends UTC with Z. On the branch an offset-less string stays a string in models, is parsed in the device zone by asTeamDate and renders empty in <app-date-time>. Confirm the backend always emits Z.

C8 · Headers

Unchanged. The branch name says "headers" but no team-zone header was ever sent; the only team header is X-Selected-Team. All zone logic lives in the frontend.
